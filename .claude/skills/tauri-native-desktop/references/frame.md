# Frame, title bar, startup and materials

Part of the tauri-native-desktop references: versions, scope and limits are in [guide.md](guide.md). Bracketed names are sources; their URLs are in [sources.md](sources.md).

On Windows start from `decorations: true`, removing the duplicate HTML title bar. A custom title bar is a legitimate choice with integration costs: Microsoft shows Snap Layouts automatically only with the system maximize button; a custom bar needs platform-drawn caption buttons or `WM_NCHITTEST` hit testing returning `HTMAXBUTTON` over the maximize region. Tauri 2.12.5 offers neither a Window Controls Overlay nor an `HTMAXBUTTON` hit test for HTML buttons, and WebView2's Window Controls Overlay API appeared only as experimental in prerelease SDK 1.0.3415, with no promotion found up to 1.0.4314.35. So with `decorations: false` and HTML buttons, Snap Layouts on hovering maximize does not appear without dedicated Win32 code. VS Code enabled the overlay for everyone in 1.71 precisely so that "Windows 11 users can use Snap Layouts". A JavaScript handler that maximizes does not by itself prove Snap is available. Keep the minimum window width at most 500 effective pixels (330 recommended) so the window fits the snap zones. Also verify Win+Z, Alt+Space, double click, dragging, resize, activation and DPI. [Tauri], [Microsoft Snap], [SDK 1.0.3415-prerelease], [VS Code 1.71].

A dark system frame needs no app code. tao (checked in 0.37.2) sets `DWMWA_USE_IMMERSIVE_DARK_MODE` on each window, following the system theme or the theme given with the `theme` option or `set_theme`. An app with its own theme setting passes that choice to `set_theme`, on a window or on the app handle for all of them; without it the frame follows the system while the page follows the app. [tao dark_mode.rs].

On macOS `titleBarStyle: overlay` can blend the content while keeping the traffic lights. `trafficLightPosition` is macOS-specific, requires overlay and `decorations: true`; reserve space in the layout. Overlay limits: the bar height varies across macOS versions, a drag region is mandatory and the window cannot be dragged while unfocused ([tauri#4316]); use `Transparent` if no HTML needs to sit under the bar. Decide explicitly `hiddenTitle` (with overlay, the unified-toolbar look), `tabbingIdentifier` (without it automatic tabbing is disabled), `acceptFirstMouse` (default `false`) and `allow_link_preview` (default `true`; turn it off to avoid the Force Touch preview on UI links). Use the app menu and predefined roles instead of copying the Windows model; give the Window and Help submenus the predefined ids `__tauri_window_menu__` and `__tauri_help_menu__` to get NSApp's window list and Help search. Predefined menu items are not portable across platforms: the list is in [os-integration.md](os-integration.md). [Window API], [Menu API], [TitleBarStyle source], [menu ids], [WebviewWindow source].

On Linux declare the supported environments. The window manager can ignore properties; shadows, effects and positioning do not have identical support across X11 and Wayland. Test the shipped desktops, and avoid needing a visual effect to distinguish windows or focus. If the project ships on Wayland, decide `app.enableGTKAppId`: with `true` the `identifier` becomes the GTK application ID, which "makes Wayland compositors and GNOME show the correct icon and application name, and group the windows", but the session-bus registration blocks a second instance (hence default `false`): pair it with the single-instance plugin. Make the `.desktop` file name, application ID and badge path match; the bundler's `StartupWMClass` only applies to X11. For WebKitGTK rendering defects with NVIDIA, Tauri lists, in order of cost, `__NV_DISABLE_EXPLICIT_SYNC=1`, `WEBKIT_DISABLE_DMABUF_RENDERER=1`, `WEBKIT_DISABLE_COMPOSITING_MODE=1`: set them only after reproducing the defect. [Tauri configuration], [enableGTKAppId source], [desktop template], [Linux graphics issues], [GTK transient].

## Startup and background

Electron recommends showing the window after the first paint, or showing it at once with a `backgroundColor` close to the app's, to "make the app feel more native" ([Electron BrowserWindow]). In Tauri `background_color` sets "the window and webview background color", but on Windows alpha is ignored for the window layer and on macOS it is "Not implemented for the webview layer" ([WebviewWindowBuilder]). WebView2 documents that setting the color through the API after creation "can still leave the app with a white flicker"; the `WEBVIEW2_DEFAULT_BACKGROUND_COLOR` environment variable (AARRGGBB) avoids it for the whole process, and the controller's creation option avoids it per window ([ICoreWebView2Controller2]).

If the first frame shows a background different from the app's theme, choose a strategy per platform. Windows: create the window with `visible: false` and give the builder, or the window config before `build()`, the `background_color` of the theme the app is about to start in; show the window when the frontend signals its first paint (for example a command the page invokes after its first render; showing right after the native color is set is the simpler variant, and leaves that color on screen until the page draws). wry passes that color to WebView2 in the controller's creation options (`ICoreWebView2ControllerOptions3::SetDefaultBackgroundColor`, checked in 0.57.1 and 0.57.2): it is the early-initialization path Microsoft offers besides the environment variable, and it is per window. A color set after creation with `set_background_color` goes through the API that can still flicker. A `transparent` window needs no color: wry gives it a fully transparent default background itself (checked in 0.57.1). A theme chosen in the app, not taken from the system, is known only to the page: persist it where the native side reads it before it builds the first window (for example a small file in the app's data directory, written by a command whenever the setting changes). `WEBVIEW2_DEFAULT_BACKGROUND_COLOR` is the fallback if a flash persists, at a cost: it overrides the creation option of every WebView the process creates and sets the color only once, so every window starts on that one color and gets its own afterwards through the property. In an app that also has a transparent window that means an opaque first frame there (inferred from the documented precedence and wry's source, not observed): prefer the per-window option. The effect on the flash was not measured frame by frame: record the startup at 60 fps on the target. [ICoreWebView2ControllerOptions3], [wry 0.57.2 source]. macOS: since `background_color` does not reach the webview layer, the background CSS must be inline and applied before the first paint. Everywhere declare `color-scheme` in the document before any CSS or JS. Apply the same policy to every window created after startup.

```rust
// Illustrative, compile against your lockfile. The process-wide fallback: Windows, before the
// first WebView is created. Not for an app with a transparent window (see above).
// In Rust edition 2024 set_var is unsafe: call it at the start of main, before spawning threads.
#[cfg(windows)]
unsafe { std::env::set_var("WEBVIEW2_DEFAULT_BACKGROUND_COLOR", "FF1E1E1E"); }
```

```html
<meta name="color-scheme" content="light dark">
<style>html{color-scheme:light dark;background:Canvas;color:CanvasText}</style>
```

## Custom drag regions

`data-tauri-drag-region` acts only on the element it is applied to (`deep`, from 2.11.0, extends it to non-clickable children) and requires `core:window:allow-start-dragging`: grant it only to the windows that use it, and keep text in the region non-selectable. On Windows the docs also suggest `app-region: drag` on the same elements for touch and pen. wry enables `IsNonClientRegionSupportEnabled` (checked in 0.53.5 through 0.57.2), so `app-region` takes effect in Tauri's WebView2. Tauri does not add it by itself: 2.0.0-beta.22 reverted that because `app-region: drag` treats the whole area as a title bar and blocks clicks on the buttons inside. Apply it by hand, mark interactive children `app-region: no-drag` and test them. On macOS the docs recommend the transparent title bar over a custom bar. [Window customization], [ICoreWebView2Settings9], [wry 0.57.2 source], [tauri CHANGELOG].

## Materials and effects

Mica, acrylic, vibrancy and Liquid Glass are optional. All effects require `transparent: true` and are not supported on Linux. On macOS they include `LiquidGlassRegular` and `LiquidGlassClear`, combinable with a classic material that Tauri falls back to on macOS 15 and below; the `interactive` option requires macOS 27. The mixed syntax (for example `effects: ["liquidGlassRegular", "sidebar"]`) is inferred from `rename_all = "camelCase"` and was not tested. On Windows `no_redirection_bitmap` sets `WS_EX_NOREDIRECTIONBITMAP`, avoiding the white flash of transparent windows, and `shadow` on undecorated windows adds the Windows 11 1 px border and rounded corners. [Effects config], [tauri#14454], [Windows builder].

Mica falls back to a solid color when transparency is off in Settings, in battery saver, on weak hardware, when the window is inactive and below build 22000; in high contrast the user's chosen background shows. DWM handles that fallback only for the backdrop: the HTML on top of a transparent window must paint its own opaque colors, and the page can detect almost none of these states. [Mica].
